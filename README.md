# CoreStudio — Pilates Studio Management Platform

Studio management for a pilates studio in Ghana, split into three projects
in this repo:

- **`backend/`** — REST API, Prisma/PostgreSQL, all business logic. The only
  thing with database access.
- **`admin/`** — staff admin portal (`/admin`), public marketing page (`/`),
  and auth pages (`/login`, `/signup`, `/forgot`). A Next.js app that talks to
  `backend` both directly (Server Components import its code as a workspace
  package) and over HTTP (client-side `fetch("/api/...")`, proxied to
  `backend` — see `admin/next.config.ts`).
- **`mobile/`** — the member-facing app (React Native / Expo), replacing the
  old mobile-first PWA. Talks to `backend` only over its REST API
  (`/api/app/**`), authenticating with a bearer JWT instead of a session
  cookie.

## Stack

Next.js (App Router) · TypeScript · PostgreSQL + Prisma · NextAuth (Auth.js,
admin/web only) · `jose` JWTs (mobile) · Tailwind CSS · Expo / React Native ·
Paystack (card + MTN/AT/Telecel MoMo, GHS) · Arkesel/Hubtel SMS · Zod ·
Vitest · Docker Compose (backend + admin + postgres + nginx + cron).

## Getting started (dev)

Prerequisites: Node 20+, Postgres 16 (local/WSL or Docker), and Expo CLI
(`npx expo`, no global install needed) if you're running the mobile app.

```bash
# 1. Install all workspaces (backend + admin) from the repo root
npm install

# 2. Postgres via Docker (or point at any local Postgres):
docker compose -f docker-compose.dev.yml up -d

# 3. Configure env — each app has its own .env (see each .env.example)
cp backend/.env.example backend/.env   # fill in AUTH_SECRET at minimum
cp admin/.env.example admin/.env       # same AUTH_SECRET as backend/.env

# 4. Migrate + seed (runs against backend/'s DATABASE_URL)
npm run db:migrate
npm run db:seed

# 5. Run both apps together
npm run dev
#   backend → http://localhost:4000
#   admin   → http://localhost:3000
```

For the mobile app:

```bash
cd mobile
npm install
cp .env.example .env   # EXPO_PUBLIC_API_URL — use your LAN IP, not localhost,
                        # when testing on a physical device
npx expo start
```

This scaffold was hand-written rather than generated by `create-expo-app`, so
before relying on it, run `npx expo install --check` inside `mobile/` to let
Expo reconcile the declared package versions against the SDK it resolves.

## Architecture notes

- **Roles**: OWNER, ADMIN, TRAINER, MEMBER. Staff (OWNER/ADMIN/TRAINER) use
  `admin/`; only MEMBER accounts use `mobile/`. Admin route access is
  enforced in `admin/src/proxy.ts` and per-route via `requireRole()` in
  `backend/src/lib/rbac.ts`; mobile route access uses `requireMobileAuth()`
  in the same file, verifying a bearer JWT instead of a cookie session.
- **Auth**: NextAuth (Auth.js v5) runs in `admin/` — that's where the
  browser's `signIn()` call and session cookie live. `backend/src/auth.ts`
  is a verification-only NextAuth instance (no Credentials provider) used
  by `requireRole()` to check the same cookie for staff-facing API routes,
  the same pattern `admin/src/proxy.ts` uses. Mobile gets its own path:
  `POST /api/app/auth/login` issues a 30-day JWT (`backend/src/lib/mobile-auth.ts`,
  signed with `AUTH_SECRET`), checked via `Authorization: Bearer <token>`.
  Both paths share the same bcrypt/credentials check
  (`backend/src/lib/verify-credentials.ts`).
- **Money** is stored as integer **pesewas** everywhere (fields keep the
  `GHS` suffix from the domain spec; `formatGHS`/`parseGHS` in
  `backend/src/lib/money.ts` convert for display/input — `mobile/lib/money.ts`
  mirrors the display half on-device). No floats.
- **Booking engine** (`backend/src/lib/booking.ts`): credits → wallet →
  Paystack; full sessions waitlist; cancellation refunds (credit back, or
  paid amount to wallet); waitlist promotion (auto via credit, else a 2-hour
  payment window). All mutations run in transactions with a `FOR UPDATE`
  lock on the session row, and every mutation writes an `AuditLog` row.
- **Payments** (`backend/src/lib/payment-flows.ts`): Paystack checkout for
  bookings, renewals and waitlist claims. The webhook
  (`/api/webhooks/paystack`) verifies the HMAC-SHA512 signature and is
  idempotent (keyed on `Payment.paystackRef`); `GET /api/app/pay/verify`
  (called by the mobile app) and the browser-facing
  `GET /api/app/pay/callback` fulfil the charge too if the webhook hasn't
  arrived, safely. The waitlist-claim SMS link now points at
  `admin/src/app/pay/[bookingId]/page.tsx` (a small session-gated web
  fallback), not the old `/app` PWA route.
- **Payouts** (`backend/src/lib/payouts.ts`): a booking is payout-eligible
  when paid (`amountGHS > 0`), ATTENDED (or BOOKED on a COMPLETED session),
  and not in any `PayoutLine`. The unique constraint on
  `PayoutLine.bookingId` makes double-payouts impossible. Statements export
  as PDF via a dependency-free writer (`backend/src/lib/pdf.ts`).
- **Scheduled jobs** (`backend/src/lib/cron-jobs.ts`, `POST /api/cron` with
  `Authorization: Bearer $CRON_SECRET`): generate sessions 4 weeks ahead from
  weekly recurrence rules, auto-complete finished sessions (un-checked
  bookings → NO_SHOW), expire 2-hour waitlist offers and promote the next
  member, renew/freeze plan cycles (3-day grace), and send 24h/2h booking
  reminders plus 3-day renewal reminders. The compose stack's cron container
  hits `backend` directly (not through `admin`) every 5 minutes.
- **SMS** is abstracted behind `NotificationService`
  (`backend/src/lib/notifications`): `arkesel`, `hubtel`, or `console` (dev).
- **Timezone**: Africa/Accra is UTC+0, so times are stored and rendered in
  UTC 1:1. If the studio ever changes timezone, revisit
  `backend/src/lib/dates.ts`.
- **Why `admin` has direct database access**: rather than force every admin
  page through the REST API, `admin/`'s Server Components import
  `backend/src/lib/**` directly (via the `@backend/*` path alias / workspace
  dependency) — the same pattern the app used before the split, per Next.js's
  own guidance to fetch Server Component data from its source, not through a
  Route Handler. Only `mobile/` is a true REST-only client.

## Deployment (DigitalOcean droplet, Docker Compose)

The whole production stack (nginx + admin + backend + postgres + cron) is
already defined in `docker-compose.yml` — a basic droplet is enough to run it.

1. **Create the droplet.** Ubuntu 24.04 LTS, Basic plan (2GB/2vCPU is enough
   to start), add your SSH key at creation. SSH in as `root` (or your sudo
   user).
2. **Install Docker.**
   ```bash
   curl -fsSL https://get.docker.com | sh
   # docker compose (the plugin, not docker-compose) ships with the script above
   ```
3. **Firewall.** Only SSH, HTTP (and HTTPS once you add TLS — see below) need
   to be reachable; Postgres/backend/admin are container-network-only
   already (confirmed in `docker-compose.yml` — only `nginx` publishes a host
   port).
   ```bash
   ufw allow OpenSSH
   ufw allow 80/tcp
   ufw enable
   ```
4. **Clone and configure.**
   ```bash
   git clone https://github.com/markyalla/corestudio.git
   cd corestudio
   cp .env.example .env
   ```
   Fill in `.env`:
   - `POSTGRES_PASSWORD` — a strong, unique value (nothing enforces this in
     code — it's on you).
   - `AUTH_SECRET` — `openssl rand -base64 32`.
   - `CRON_SECRET` — `openssl rand -hex 24`.
   - `ADMIN_PUBLIC_URL` / `BACKEND_PUBLIC_URL` — the droplet's IP for now
     (e.g. `http://<droplet-ip>`) since there's no domain yet; switch both to
     `https://<your-domain>` once you add one (see below).
   - `PAYSTACK_SECRET_KEY` / `PAYSTACK_PUBLIC_KEY` — live keys.
   - `SMS_PROVIDER` + the matching `ARKESEL_API_KEY` or
     `HUBTEL_CLIENT_ID`/`HUBTEL_CLIENT_SECRET`.
5. **Build and start.**
   ```bash
   docker compose up -d --build
   ```
   Only the `backend` container applies migrations on boot
   (`backend/docker-entrypoint.sh`).
6. **Create the first OWNER account.** Do **not** run `db:seed` against
   production — it hardcodes `password123` for every account it creates,
   OWNER included. Instead:
   ```bash
   docker compose exec backend sh -c \
     "OWNER_NAME='Your Name' OWNER_EMAIL='you@example.com' OWNER_PHONE='+233...' OWNER_PASSWORD='a-real-password' \
      ./node_modules/.bin/tsx prisma/create-owner.ts"
   ```
7. **Paystack webhook.** Point it at
   `http://<droplet-ip>/api/webhooks/paystack` (or the HTTPS URL once you
   have a domain).
8. **Mobile app.** A separate release (App Store / Play Store, or an Expo EAS
   build) — not part of this compose stack. Point its `EXPO_PUBLIC_API_URL`
   at the same public URL (nginx forwards `/api/*` through to `backend`).

### Adding HTTPS later

The stack currently serves plain HTTP on port 80 — fine for an IP-only
deployment, not fine once real user traffic/credentials are involved. Once a
domain points at the droplet:

1. `ufw allow 443/tcp`.
2. Get a certificate (`certbot --nginx` if you install certbot on the host, or
   run it as a companion container against nginx's webroot).
3. Add a `server { listen 443 ssl; ... }` block to `nginx.conf` with the
   cert/key paths, plus a `server { listen 80; return 301 https://...; }`
   redirect for the existing block.
4. Switch `ADMIN_PUBLIC_URL`/`BACKEND_PUBLIC_URL` in `.env` to `https://...`
   and `docker compose up -d` to pick up the change.
5. Consider adding a `Strict-Transport-Security` header in
   `admin/next.config.ts`'s `headers()` once TLS is confirmed working (it's
   deliberately not there yet — sending HSTS over plain HTTP is a footgun if
   TLS is ever removed).

## Testing

- `npm test` (from the repo root, or inside `backend/`) — Vitest tests
  covering the critical business rules: credit consumption, waitlist
  promotion order, payout exclusion of already-paid bookings, and
  cancellation-cutoff enforcement. They run against a separate
  `corestudio_test` database (created automatically).
- The old Playwright browser E2E test drove the `/app` PWA directly and no
  longer applies now that member booking happens in `mobile/`. There's no
  automated E2E coverage for the booking flow yet — validate it by running
  the Expo app against a local `backend` (see Getting started) or by
  scripting the `/api/app/**` endpoints directly.
